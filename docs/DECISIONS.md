# Journal des décisions

Décisions prises pendant l'implémentation, non couvertes (ou amendées) par `docs/PLAN.md`.

| Date | Décision | Raison |
|---|---|---|
| 2026-09-27 | Clé Notion `Url_CalCom` renommée en `Url_Booking` (lue par `fetch-content.ts`). | Demande d'Arthur : Cal.com n'est qu'un choix technique actuel, potentiellement remplacé (ex. Doctena). Un nom de clé neutre évite de coupler le schéma Notion à un prestataire. |
| 2026-09-27 | `SiteContent.booking` devient `{ url, provider: "cal" \| "generic", calLink, calOrigin }` au lieu de `{ url, calLink, calOrigin }` toujours Cal.com. `provider` est déduit de l'hôte de l'URL Notion (liste blanche `cal.eu` / `app.cal.eu` / `cal.com` / `app.cal.com`) dans `parseBookingUrl` (`src/lib/content/parse.ts`, remplace `parseCalUrl`). | Rend la prise de RDV générique et configurable comme demandé : changer de prestataire (ex. coller une URL `doctena.lu`) ne demande aucun changement de code — seuls les hôtes Cal.com connus activent l'intégration embarquée (popup + agenda inline, §9 du plan) ; tout le reste reste un vrai lien `<a href>` (règle non négociable 6), ce qui est un dégradé propre et non une régression. |
| 2026-09-27 | Écart avec `parseCalUrl` du plan (§6.4) : un hôte inconnu n'est plus supposé être une instance Cal.com auto-hébergée (`${protocol}//${host}` comme `calOrigin`) ; il devient `provider: "generic"`. | Aucune instance auto-hébergée n'est utilisée aujourd'hui ; deviner qu'un hôte inconnu est « Cal.com quand même » contredit l'objectif de généricité demandé et risquerait de tenter un embed Cal.com contre un domaine qui n'en est pas un (ex. Doctena). |
| 2026-09-27 | `scripts/seo-smoke.ts` (§6.13) : le contrôle des liens de RDV vérifie `a[href === content.booking.url]` (URL réellement configurée dans Notion, lue via `getSiteContent()`) au lieu du motif figé `/cal\.(eu\|com)\//` du plan. | Cohérent avec la généricité de la prise de RDV : le smoke test reste correct quel que soit le prestataire configuré dans Notion, sans modification si Cal.com est un jour remplacé. |
| 2026-09-27 | Ajout d'une règle CSS `@media (prefers-reduced-motion: reduce) { [data-reveal] { opacity: 1 !important; transform: none !important; } }` dans `globals.css`, en complément de `MotionConfig reducedMotion="user"`. | Vérifié (Playwright, `reducedMotion: "reduce"`) : la bibliothèque `motion` ne neutralise que les animations de position/transform (x, y, scale…) sous mouvements réduits, pas l'opacité (code source : `shouldReduceMotion && positionalKeys.has(key)`). Sans ce correctif CSS, les cartes `Reveal` continuaient de s'estomper en fondu (opacity 0→1 sur 500 ms) malgré la préférence système, ce qui contredit la règle non négociable 4 (« aucune animation », § validée manuellement : opacity reste à 1 en continu avec le correctif). |
| 2026-09-27 | Phase 7 (QA) : forme décorative du hero (`hero.tsx`) rendue responsive — `inset-0` (pas de décalage, pas de rotation) en dessous de `sm`, `-inset-3 rotate-2` (valeurs du plan) à partir de `sm:`. | Un test Playwright automatisé (largeurs 320/360/390/768/1024/1280/1440 px) a détecté un débordement horizontal réel de la page à 320 px (18 px), causé par cette forme `-inset-3 rotate-2` associée au hero : à cette largeur, la colonne image touche déjà la marge de 16 px, et le décalage négatif + la rotation la faisaient sortir du viewport. Résiduel après correctif : 1 px (arrondi sous-pixel, non perceptible, sans effet sur `overflow-x`). |
